# Adobe / Open Format Compatibility Architecture

## 方針と現在地

外部形式は入出力アダプターで扱い、LumaPaintの文書正本をPSD・AI・PDFへ置き換えない。正本はRust側のDocument／タイル文書、表示と変換はRust側のRenderer／Workerが担当する。WebViewには設定、進捗、能力、変換レポートを送る。画像本体・タイル・外部ファイルの大容量ペイロードはRustに保持する。

既存の[非破壊文書契約](non-destructive-document.md)、[タイル契約](tile-engine.md)、[v1保存仕様](project-format.md)を優先する。v1 JSONと`LPTILE2\0`コンテナは現在別モデルであり、単一の完成済み上位モデルとは称さない。コンテナの識別名と内部バージョン番号も区別する。今回の変更は既存保存形式や既存文書を移行しない。

RGB／CMYKと8／16／32bitの設定値は、実際のCMYK画素、ICC色変換、高精度タイルを実装した証明にならない。現行タイルはRGBA8。ページ／タイムライン／ネストしたレイヤーグループは段階的な拡張対象。ベクターのオブジェクトグループとPSDのレイヤーグループを同一視しない。

## 依存方向

```text
Tauri host (dialog, worker, cancellation, document adoption)
    ↓
lumapaint-formats (probe, parser, mapping, conversion report)
    ↓
lumapaint-core (native document validation, tiles, graph, history)

lumapaint-renderer → lumapaint-core
```

コアは外部アダプターやTauriに依存しない。形式処理をUI・Documentの編集メソッドへ混ぜない。最初は`lumapaint-formats::psd`の独立モジュールとし、依存や実装規模が増えた場合にPSD／PDF／ORA等を別crateへ分割する。まだない各形式の空crateや空の上位Nodeを大量に追加しない。

`DocumentImporter::probe`は署名検出だけで、正常ファイル・読込可能・編集可能の保証ではない。`import`は検証済みのネイティブ状態と`ConversionReport`を返す。ホストはワーカーの結果を全検証した後に新しい文書として採用する。入力失敗・取消で既存文書を変更しない。新規取込の履歴は文書作成を起点とし、元PSDの履歴を捏造しない。

Exporterは後続実装とし、元文書の読み取り専用スナップショット、出力設定、レポートを受け渡す。書出しはネイティブ保存と分離し、成功しても`.lumapaint`正本の保存済みrevisionを更新しない。一時ファイルへの出力を完了してから原子的に置換する。

## 互換レポート

| Tier | 判定基準 |
| --- | --- |
| A | 対象機能の編集性と見た目を往復試験で維持。単にヘッダーや画素を読めたことでは付与しない |
| B | 編集可能だが、具体的な差異・代替処理がある |
| C | 合成画像等による見た目のフォールバック。元の編集性は失われる |
| D | 未対応・破棄・変換不能の情報。色プロファイル破棄では見た目の一致も保証できない |

判定は形式全体への宣伝文句ではなく、ファイル中の機能・変換方向・実装版・試験条件ごとに記録する。CやDを警告なしで通さない。`allow_lossy`は呼出側が損失を承認した場合だけ設定し、GUIでは具体的なレポートを表示して選択させる。空レポートを自動的にTier Aとして表示しない。

レポートは安定コードとTierを持つ。UI接続時に英語・日本語・简体中文の表示へ変換し、必要に応じて元レイヤーID・機能名・代替操作・検証条件を追加する。文書の画素をWebViewへ送って診断しない。

## 現在の実装と未対応範囲

| 形式／機能 | 現在 | 次の境界 |
| --- | --- | --- |
| PSD v1 RGB8・3チャンネル・不透明の合成画像 | 独立RustアダプターでRaw／PackBits RLEをネイティブRGBA8タイルへ変換 | macOSワーカーと新規タブへの採用 |
| PSDレイヤー／グループ／マスク／文字／図形 | 未解析。レイヤー領域がある場合は統合の警告Cを返す | レイヤーレコード・各チャンネルの検証とマッピング |
| PSD解像度・ICC・その他リソース | リソース境界を検査。保持しない項目は警告D | メタデータ／バイナリアセットの保持とICC変換 |
| PSD追加チャンネル・透明度・CMYK・16/32bit・ZIP／PSB | 明示的に拒否 | チャンネルの意味と高精度／色管理を実装してから拡張 |
| PSD出力 | 未実装 | RGB8ラスターレイヤー出力から着手、Photoshopとの往復試験 |
| SVG | 現行の保持・描画を維持。外部SVGの編集可能オブジェクトへの完全変換は未対応 | 線・文字・クリップ・グループ・画像の往復差異を記録 |
| PDF／PDF互換AI | 未実装 | PDFを共通境界にし、AI固有データは別能力として扱う |
| OpenRaster | 未実装 | レイヤー画像＋順序＋基本設定。ZIP展開上限と相対パス検査 |
| IDML／アニメーション交換 | 未実装 | ネイティブのページ／Story／時間軸が成立してから対応 |

最初のPSDアダプターはライブラリ境界のみ。現時点で「ファイル → 開く」はPSDを選択できない。合成画像を読めてもPhotoshopのレイヤー編集互換や往復互換とは表示しない。画像リソースとレイヤーの内部データは保持されない。

## 最初のPSD契約

[Adobe Photoshop File Formats Specification](https://www.adobe.com/devnet-apps/photoshop/fileformatashtml/)を参照。ヘッダー・長さ付きセクション・合成画像は別々に検証する。

入力上限512MiB、ネイティブ寸法上限各辺8192px。Rawは期待長と一致すること、RLEは行長表・各行の正確な展開幅・末尾を検証する。タイルを確保する前に圧縮画像の展開量を確認する。行単位でRGBをタイルへ書き込み、別の全画面RGBAバッファを作らない。端タイルの用紙外はゼロ。画素の正本はRGB8をRGBA8へ写したもので、アルファは255。

形式上の限界とアプリの限界を分離する。署名一致、ヘッダー正常、セクション構造正常、デコード成功、文書採用、表示一致、往復互換はそれぞれ別の達成段階。レイヤー領域は現段階では長さ境界だけを検証するため、PSD全体の意味的な検証済みとは称さない。

## 実装順と完了条件

1. [Done] 依存方向、現行モデルの制約、Tier基準を明文化。独立インポーターと損失レポートを追加。
2. [Done] PSDの不透明RGB8合成画像をRaw／RLEからタイルへ変換。切断・過剰展開・上限・情報欠落を検証。
3. [Next] macOSの開くワーカーへ接続。損失内容を三言語で提示し、承認済み結果だけ新規タイルタブへ採用。取消・エラー・既存文書維持・復旧・保存再読込を検証。
4. [Next] PSDラスターレイヤー・名前・可視性・不透明度・順序・透明度・マスク。まずRGB8、通常合成に対象を限定。未対応描画モードを通常へ黙って変更しない。
5. [Later] PSD出力とPhotoshop生成の実ファイルによる往復試験、OpenRasterのレイヤー交換、SVG往復強化。
6. [Later] ICC／CMYK／高精度画素、PDF／PDF互換AI、ページモデル成立後のIDML、時間軸成立後のアニメーション交換。
7. [Later] ネイティブコンテナの独立した公開仕様とreference library。現在の実装を仕様化してからC ABI／WASMを検討。

合成画像の最初の試験は合成fixtureであり、Photoshop生成ファイルとの相互運用は未検証。実ファイルのコーパスには日英中の名前・端タイル・透明度・重なり・マスク・ICC・各圧縮方式・不正長・往復保存を含める。将来のTier Aはこの証拠とともに公開する。
