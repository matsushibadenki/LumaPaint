# Continuous drawing and pan — transport validation

The implementation retains the oldest unpresented request time while the foreground renderer's serial is unchanged. New pointer events update the recent-input time but cannot restart the same pending deadline indefinitely. The first candidate used 8ms pending/16ms background-service eligibility during a held gesture. Four accepted Release trials showed increased first-event pan latency, so that candidate was rejected. The final policy retains the established 32ms pending/50ms service eligibility and 80ms recent-input limit, including while a button remains held without movement. These are scheduler eligibility/soft-budget values, not hard deadlines or per-pane FPS guarantees.

Inactive standard panes now reuse their last successful presentation when canonical revision and the complete viewport match. View position/visibility and occlusion masks still update. Hidden/recreated surfaces, changed viewport/DPI/color/revision, failed presentation and tiled documents bypass this reuse. Animation frames continue through their existing native clock; unrelated active-document notifications no longer force repeated renders of the same inactive picture. Source-fork preparation before the reuse check remains a later optimization.

Pan input now records native event ages and `pan_down`/`pan_drag`/`pan_up` stages. Zero-displacement or non-finite pan deltas do not schedule a new frame. This instrumentation and no-op suppression are common to both comparison modes. `LUMAPAINT_PANE_CONTINUOUS_PRIORITY=0` disables the new continuous policy and retained-picture reuse for a same-binary control; production defaults to enabled. The earlier sparse-input priority stays enabled in both modes.

## Excluded probes and accepted transport

The native GUI automation drag looked like a held movement in wall-clock operation, but its actual NSEvent timestamps span only **0.164–0.844ms** per gesture. Sixteen short drag probes produced 16 presentations, not a sustained 60Hz stream. They are diagnostic evidence, not accepted continuous-input timing. The temporary paint layer was undone/discarded without saving the owned fixture files. The probe and its explicit exclusion reason are preserved in [the evidence JSON](continuous-input-validation-2026-10-25.json).

The user explicitly authorized a timed native-input driver. An external process-targeted Quartz probe completed its send calls but delivered zero native input events to LumaPaint; no security/accessibility settings were changed. A safer app-contained transport was therefore prepared as the `native-input-qa` Cargo feature. It is absent from ordinary builds and checks the QA application identifier, `main` editor window, canonical owned Pane-1 path, tool, current document identity, foreground state and small native viewport geometry. New runs/window close cancel queued work through generation-specific cancellation identity.

A 60Hz producer thread schedules timestamped events through Tauri's main-thread dispatcher and AppKit's normal event queue. It does not invoke document paint/pan methods directly. The hidden QA-only Command-Shift-F10 trigger reads a bounded, strict JSON plan from `/tmp/lumapaint-native-gesture-plan.json`. Plan fields are `tag`, `kind` (`draw`/`pan`), `gestures` (1–16) and `seconds` (0.5–3). The protocol requests sixteen one-second gestures with 150ms gaps, discards the first two gestures, and records both first/latest-handler times, matching event ages, coalescing, background frame advancement during held input and idle recovery. Drawing uses a temporary pixel layer; pan alternates directions to return to the starting view. Synthetic app-queued events must be clearly distinguished from physical mouse/stylus input and OS input-to-photon measurements.

The Mac initially locked before transport acceptance. **After the user manually unlocked it, delivery was verified:** a one-second pilot produced down, sixty movement events and up over exactly 1000ms of NSEvent source timestamps. Visible brush marks appeared in the native canvas. The four initial old/new/new/old trials each completed sixteen one-second drawing gestures and sixteen alternating pan gestures. All down/up pairs and sixty movements per gesture were received. Temporary strokes/layer creation were undone, QA changes were discarded, and pan returned to the same stored view. The first two gestures per phase are warmup, leaving 28 gestures per operation per mode.

The initial policy's rejected measurements remain in [the candidate evidence](continuous-input-rejected-policy-2026-10-25.json). First-handler pan p95 increased from 1.626ms to 17.670ms. Its nominal drawing p95 reduction was accompanied by a 975.803ms first-handler maximum in one trial. Background idle frequency also varied substantially. Concurrent system/other-project load was observed and was not stopped; these measurements do not establish a general performance gain. The more aggressive service policy is absent from the final implementation. See [the final Release comparison](continuous-input-release-2026-10-25.md) for the conservative policy and retained-presentation results.

Normal library regression: 222 passed / 2 ignored. Tests cover repeated-request deadline retention, continuous service eligibility and return to idle. Normal optimized Release and QA-feature Release builds pass; all-target QA-feature Clippy with warnings denied passes. Formatting, architecture boundary, document-layout model and the five existing latency summarizer tests pass. The QA binary/source hashes and excluded probe are recorded in the JSON. Timed AppKit runtime delivery is verified. Long-held physical pen input, complex artwork and Windows/Linux/multi-display acceptance remain unverified.

The final conservative comparison completed after the second manual unlock. Four accepted launches, plus one documented foreground-loss interruption/restart, are recorded in the final report. Both enabled drawing phases skipped 128 redundant pane renders; all backgrounds progressed and all pan views returned exactly. Final results do not establish a general latency or CPU gain. The manual-lock blocker is resolved; physical input and the broader workloads listed above remain unverified.
