# Document pane arrangement — 2026-10-25

The document area now has a view-only grid of tab groups (1–3 rows and columns). Document content, selection, history and editing remain in the existing Rust session. Each group selects a document; only the globally active group hosts the existing native wgpu canvas. Inactive groups display a bounded 1024px full-document PNG generated on a Rust worker and fetched through an opaque `document-preview` resource URL. Clicking a preview activates that document. The initial version fitted the active document after layout changes; the view-retention follow-up below preserves zoom and pan instead. This is not a separate GPU renderer or independent viewport for every group.

Tab dragging uses pointer capture, with a six-pixel activation threshold. A nearest-edge zone selects horizontal or vertical splitting; center drops move a tab into a group. At three rows/columns, further splits in that direction become moves. The native canvas is hidden during the drag so it cannot intercept the WebView drop. Pointer-up, cancellation, lost capture, Escape and window blur restore normal visibility. The initial HTML5 drag implementation failed to receive a reliable drop/end notification under Tauri; it was replaced before acceptance. The grid retains empty cells for later drops; consolidating restores a single tab group. Presentation layout is kept in React; it does not copy document state or editing history. Layout persistence remains a follow-up; per-document zoom/pan is implemented below.

Native acceptance used an owned debug bundle `app.lumapaint.document-panes-qa`, embedded `tauri://localhost`, actual WKWebView and Apple M4/Metal in a 1200×800 window. No IPC mock or browser imitation was used. CUA connected to the initial app with an unusually long tool wait; subsequent snapshots displayed the UI. That tool wait is not an application input-latency result. The host logged a nonfatal sandbox-extension warning, but file dialogs, Metal rendering and custom preview resources worked. JavaScript console logs were not captured; screenshots and native accessibility state showed no framework overlay or preview failure.

Three owned fixtures contained a red, green or blue rounded rectangle. Native file dialogs opened each. Blue tab → right edge produced two columns; Green tab → the inner right boundary produced three columns. Non-active Red/Blue previews and active Green appeared together. Clicking Blue activated its native canvas; one stroke was drawn and saved. Switching to Red kept its stroke count at zero while Blue's preview showed the new line. After quitting/relaunching, Blue still had one saved stroke and Red/Green had zero.

The arrangement menu was used for three rows and consolidation. Green tab → lower outer edge then Blue tab → the horizontal inner boundary produced two then three rows. A 3×3 preset created nine groups; Red was moved into the ninth empty group. Closing Green removed only that tab. Consolidating after the final 3×3 test returned all three remaining open tabs to one group. Final auto-fit checks showed 53.59% after the first two-column split and 17.29% in a three-row active canvas, without the earlier cropped view. The arrangement menu was visible above the native canvas.

## View retention and draggable boundaries — 2026-10-25

This follow-up replaces the fit-on-every-switch behavior above. Rust keeps absolute logical-pixel zoom and pan per document in each window runtime. Parking a document records its native view; activating it restores that document's view. Closing removes stale entries after successful closure; a cancelled close retains them. The cache is exchanged with the other Rust window session fields. It does not modify document history or the native project format, and is not persisted across application restarts. Tab movement carries the document's view with it. Newly visited documents default to fit and zero pan.

Inactive preview responses now include a small view record alongside the opaque image URL. Their CSS viewport reserves the native ruler/footer insets and uses the saved zoom and pan, while the PNG remains bounded to 1024px. CPU thumbnail/native GPU antialiasing can differ; this is still a preview, not independent live GPU rendering. Active native surfaces resynchronize when an ancestor scroll container moves.

Grid weights retain the sum of each resized adjacent pair. New splits divide the target weight; arrangement presets reset track weights without resetting document zoom/pan. Separators occupy explicit 3px grid tracks, with an 8px interaction region masked out of the native surface. Pointer capture and one rAF update per frame keep the drag local; pointer-up commits the final event position, cancellation restores starting weights. Width/height minima remain 120/110px. Arrow keys move the boundary by two percentage points, Home/End clamp it, and double-click makes the adjacent pair equal. Document IDs and unrelated track weights remain unchanged.

Native acceptance reused the isolated `app.lumapaint.document-panes-qa` debug bundle, embedded Tauri UI and M4/Metal at 1200×800. Red and Blue owned fixtures were opened through native file dialogs. Red was set to 50% and panned by a native hand-tool drag; Blue was set to 100% with a different pan. Switching back restored Red's exact colored bounds: (227,336)–(466,495), both before and after switching. A +90px column-boundary drag increased the active native viewport from 391px to 481px; Red's bounds moved to (272,336)–(511,495), exactly +45px horizontally, with unchanged size. Switching Blue→Red after resize preserved these same bounds and restored 100%→50% respectively.

Double-click returned the boundary to 50%; Right moved it to 52%. A +100px horizontal-boundary drag produced a 66% top row and a 337px active native height, retaining Red at 50%. Inactive Red's preview center matched the active native center exactly; its vertical silhouette differed by one pixel per edge from CPU/GPU antialiasing. In a three-column preset, resizing boundary one changed it to 40%, while boundary two stayed 67%. Home clamped the first boundary to 15% without moving the second. No document paint operation was performed in this run. The app quit with exit code 0 and its owned temporary bundle was removed.

## Restart restoration and independent GPU panes — 2026-10-25

This follow-up supersedes the earlier CPU-only inactive-pane and session-only view limitations. Saved files are reopened from their canonical paths, with fresh runtime IDs mapped into the stored layout. Rows/columns, weights, pane tabs, selected tabs, active document, absolute zoom and pan are restored per editor window label. Startup does not replace documents already opened by the user. JSON is versioned, validated and limited to 128KiB; reopened file input is limited to a cumulative 128MiB. Missing/unreadable files are skipped with a compact warning tooltip. All loaded projects are prepared before modifying the empty workspace. No document pixels, undo history or document content are serialized in this metadata. Writes use a temporary file, sync and rename; generation checks cover both queued metadata and disk writes. Close flushes the latest native view state.

Unsaved/new documents and changes since the last file save are not automatically reopened by this metadata. Existing recovery remains their recovery mechanism. This does not automatically recreate additional windows or shared-document relationships between them. An invalid workspace setting produces a warning rather than being trusted as a layout. The test environment exercised normal restart, not power-loss recovery.

Inactive panes retain separate Metal surfaces, renderers and GPU caches. Canonical documents remain in the Rust session; rendering forks omit history. Native passive views reject hit testing and first-responder status, do not register file drops, and do not consume the main canvas's display callbacks or cursor updates. Frame masks do not replace the active canvas's hit-test mask. Monotonic request generations prevent delayed show/hide work from resurrecting cancelled surfaces. Surfaces render on document notifications, view switches and geometry/visibility changes; continuous independent timeline playback remains unfinished. Some existing renderer preparation paths can still perform CPU rasterization. No Release latency improvement is claimed.

Allocation estimates are bounded to 128MiB per pane and 256MiB per window, with at most eight retained inactive surfaces. Hidden surfaces are evicted in LRU order. Changed document dimensions/layer allocation force a new budget assessment. Each surface has an 8MiB renderer cache budget. These are estimated image/cache limits, not a strict bound on all driver/device VRAM. Failed/unavailable/over-budget surfaces show the bounded PNG fallback with an information indicator; dragging boundaries also temporarily uses that fallback. The physical run did not force adapter failure, budget exhaustion, or eight large simultaneous surfaces.

Native acceptance used the isolated debug app `app.lumapaint.document-panes-qa`, embedded production WebView assets, Apple M4/Metal, 1200×800. Red's colored bounds were exactly (272,336)–(511,495), and Blue's visible bounds (592,317)–(889,636), before and after restart. Paths and scalar view metadata were verified in the isolated app's workspace JSON. No document painting was performed in this run.

A Green fixture was added and three columns selected. Two non-active GPU views and the active native canvas displayed simultaneously. Native metrics reported separate `pane_gpu create` records for documents 2 and 3 and advancing presentation serials for both. Clicking the inactive GPU views switched editing without adding strokes.
