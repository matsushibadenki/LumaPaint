# ソフトウェア最適化・高速化・省エネ化 指示書

このプロジェクト全体を調査し、性能、応答速度、メモリ効率、CPU/GPU効率、I/O効率、電力効率を改善してください。

ただし、闇雲に最適化コードを追加してはいけません。

最重要原則は、

**「推測で最適化せず、計測してから直し、直した後に再計測する」**

です。


# 0. 最適化の目的

次の優先順位で改善してください。

1. ユーザーが感じるレイテンシ
2. フレーム時間・応答時間の安定性
3. 不要なCPU処理
4. 不要なGPU処理
5. 不要なメモリアクセス・コピー・allocation
6. 不要なI/O・IPC・serialization
7. 不要な再計算
8. 不要なwake-up / polling / background処理
9. メモリ使用量
10. 消費電力

単純なbenchmarkスコアだけではなく、

**「同じ結果を、より少ない仕事で実現する」**

ことを最終目標としてください。


# 1. 最初にコードを変更しない

まずプロジェクト全体を調査してください。

以下を把握してください。

- architecture
- hot path
- main loop
- render loop
- event loop
- data flow
- thread構成
- async処理
- IPC
- network
- storage
- database
- cache
- serialization
- memory allocation
- CPU/GPU境界
- frontend/backend境界

最初から「ここが遅そう」という理由だけで修正しないでください。


# 2. 実際のボトルネックを計測する

可能な限りprofileしてください。

CPUについては、

- CPU time
- wall time
- function call count
- allocation count
- allocation bytes
- memcpy / clone
- lock wait
- thread wake-up
- context switch

を調査してください。

GPUを使用する場合は、

- GPU frame time
- command encoding
- buffer upload
- texture upload
- draw calls
- dispatch calls
- pipeline switching
- synchronization
- CPU/GPU stall

を調査してください。

I/Oについては、

- disk read/write
- network request
- database query
- IPC
- serialization/deserialization

を調査してください。


# 3. 平均値だけを見ない

性能評価では平均値だけで判断しないでください。

可能なら、

```text
median
p95
p99
maximum
```

を記録してください。

UIでは特に平均FPSより、

```text
frame time
p95 frame time
p99 frame time
input latency
```

を重視してください。

平均60fpsでも一部フレームが50msなら操作感は悪くなります。


# 4. 処理量そのものを減らすことを最優先する

低レベルなmicro optimizationより先に、

**その処理自体を実行する必要があるのか**

を検討してください。

優先順位は原則、

```text
処理しない
↓
必要な部分だけ処理
↓
再利用する
↓
まとめて処理
↓
並列化する
↓
GPU/SIMD等で高速化
↓
命令単位のmicro optimization
```

としてください。

100msの処理をSIMDで50msにするより、

不要な処理を削除して0msにできないか先に検討してください。


# 5. O(N)を疑う

操作対象が1個なのに、

```text
for item in all_items
```

を行っていないか調査してください。

1個の変更に対して、

```text
O(N)
O(N log N)
```

が発生している場合、

```text
O(1)
O(log N)
O(K)
```

へできないか検討してください。

Kは実際に影響を受ける要素数です。

大規模データでは、

**全体ではなく変更されたものだけを処理する**

設計を優先してください。


# 6. Incremental Updateを優先する

全体再構築を避けてください。

悪い例:

```text
small change
→ rebuild everything
```

目標:

```text
small change
→ identify dirty data
→ update only affected data
```

可能なら変更を、

```text
GeometryDirty
TransformDirty
StyleDirty
ContentDirty
LayoutDirty
VisibilityDirty
StructureDirty
```

などに分類してください。

軽い変更で重いcacheまで無効化しないでください。


# 7. Cacheの存在ではなくCache Hit率を見る

「cacheを実装した」だけでは高速化とはみなしません。

必ず、

```text
cache hits
cache misses
cache invalidations
cache rebuilds
cache memory
evictions
```

を測定してください。

特に、

**毎回invalidateされるcacheはcacheではありません。**

過剰なcacheによって、

- memory増加
- synchronization増加
- invalidation複雑化
- CPU負荷増加

が発生していないかも確認してください。


# 8. 不要なallocationを調査する

hot path内の、

```text
Vec::new
String::new
clone
collect
format
Box
Arc
HashMap
HashSet
temporary buffer
```

などを調査してください。

ただし、profileで問題になっていないallocationを可読性を犠牲にしてまで削減しないでください。

必要なら、

- buffer reuse
- object pool
- scratch buffer
- arena
- small-vector
- preallocation

を検討してください。


# 9. Copyを減らす

大きなデータについて、

```text
A
→ copy
→ B
→ copy
→ C
→ copy
→ D
```

となっていないか調査してください。

可能なら、

```text
shared ownership
borrow
view
slice
reference
zero-copy
move semantics
```

を利用してください。

特に、

- image
- video
- audio
- tensor
- large string
- JSON
- GPU buffer
- database result

ではコピー量を測定してください。


# 10. Serializationを疑う

プロセス・言語・frontend/backend境界で、

```text
object
→ JSON
→ string
→ IPC
→ parse
→ object
```

を高頻度で行っていないか確認してください。

特に60/120HzのUI処理で巨大JSONを渡さないでください。

必要なら、

- binary representation
- shared memory
- compact command
- ID + delta
- batch
- retained state

へ変更してください。


# 11. CPU/GPU間転送を減らす

GPUを使っているから高速とは限りません。

毎フレーム、

```text
CPU calculation
→ large GPU upload
```

を行う設計は避けてください。

GPU上に保持できるデータは保持し、

```text
small delta
small uniform
small instance update
```

だけを転送することを優先してください。

CPU↔GPU synchronizationも最小化してください。


# 12. GPU化の前にアルゴリズムを改善する

遅いCPUアルゴリズムをそのままGPUへ移植しないでください。

まず、

```text
algorithm
data structure
update strategy
cache strategy
```

を改善してください。

その後、並列性の高い処理だけGPU化してください。


# 13. 並列化しすぎない

thread数を増やせば速くなるとは限りません。

以下を測定してください。

- synchronization
- mutex contention
- atomic contention
- task scheduling
- context switching
- cache coherence
- false sharing

小さな処理を大量のtaskへ分割して逆に遅くしないでください。


# 14. Lockを調査する

hot pathで、

```text
Mutex
RwLock
Atomic
channel
```

による待機が発生していないか調査してください。

可能なら、

```text
immutable snapshot
message passing
single writer
double buffering
lock-free read
```

などを検討してください。

ただし複雑なlock-free実装を、計測上の必要性なしに導入しないでください。


# 15. UI threadをブロックしない

UI thread/main threadでは、

- heavy computation
- file I/O
- network
- database
- image decoding
- text shaping
- large serialization
- compression
- expensive parsing

などを極力実行しないでください。

ただしworkerへ移動しただけで総処理量が増えていないかも確認してください。


# 16. Pollingを減らす

省エネのため、

```text
while true
poll
sleep
poll
```

のような処理を可能な限り避けてください。

イベント駆動、

```text
event
notification
interrupt
watch
condition variable
```

を優先してください。

何も起きていない時には、

**CPU/GPUが可能な限り仕事をしない**

状態を目標にしてください。


# 17. Idle時の消費電力を重視する

アプリを何も操作していない状態で、

- CPU使用率
- GPU使用率
- wakeups
- timers
- background threads
- redraw
- network polling

を確認してください。

Idle時に60/120fpsで意味のない再描画を続けないでください。

必要ならon-demand renderingにしてください。


# 18. 省エネを性能の一部として扱う

高速化によって消費電力が大幅に増える変更は慎重に評価してください。

例えば、

```text
CPU 5ms → 3ms
```

になっても、

CPU/GPUを常時高クロックで動かすことで達成しているなら、総合的に良い最適化とは限りません。

可能なら、

```text
work completed / joule
```

という観点でも評価してください。


# 19. Race to Idleを意識する

必要な仕事を効率良く短時間で終わらせ、その後CPU/GPUをidleへ戻せる設計を優先してください。

ただし無意味なburst並列化によって電力効率を悪化させないでください。


# 20. データ構造を見直す

大量データを扱う場合、

```text
Vec
HashMap
BTreeMap
linked structures
AoS
SoA
spatial index
BVH
R-tree
arena
```

などを比較してください。

特にhot pathではCPU cache localityを考慮してください。

必要に応じて、

```text
AoS → SoA
```

も検討してください。


# 21. DB・Networkは呼び出し回数を減らす

以下を調査してください。

```text
N+1 query
duplicate query
duplicate HTTP request
small repeated writes
unnecessary fsync
unnecessary metadata request
```

可能なら、

```text
batch
cache
prepared query
pagination
streaming
connection reuse
```

を利用してください。


# 22. Compressionは総コストを見る

データ量削減のためのcompressionが、

```text
CPU cost > I/O saving
```

になっていないか確認してください。

圧縮率だけでなく、

```text
compression time
decompression time
transferred bytes
energy
latency
```

を総合評価してください。


# 23. Release buildで測定する

debug buildの結果だけで性能判断しないでください。

実際の配布条件に近い、

```text
release
production
optimized build
```

でbenchmarkしてください。

debug instrumentation自体が測定結果を大きく変えていないかも確認してください。


# 24. 実際のデータで測定する

小さなsynthetic benchmarkだけで判断しないでください。

最低でも、

```text
small
medium
large
stress
```

のデータセットを用意してください。

アルゴリズムが大規模化したときどうスケールするか確認してください。


# 25. 性能劣化の境界を探す

単に「速い/遅い」ではなく、

```text
100
1,000
10,000
100,000
1,000,000
```

などデータ量を増加させ、

どこから急激に性能が落ちるか調査してください。

これによってO(N²)などの問題を発見してください。


# 26. 最適化前後を必ず比較する

すべての主要変更について、

```text
Before
After
Difference
Percentage
```

を記録してください。

例えば、

```text
operation        before   after    change
drag p95         21 ms     5 ms    -76%
CPU/frame        14 ms     3 ms    -79%
alloc/frame      18 MB    80 KB    -99.6%
GPU upload       64 MB     256 B   -99.99%
idle CPU          8%       0.2%    -97.5%
```

のようにしてください。


# 27. 効果のない最適化を残さない

非常に重要です。

変更した結果、

- 性能改善なし
- 誤差程度
- regression
- complexityだけ増加

だったコードは原則として残さないでください。

元に戻すことも最適化作業の一部です。

「せっかく実装したから残す」という判断は禁止します。


# 28. 最適化のために複雑化しすぎない

性能改善が小さいのに、

- abstraction増加
- cache増加
- state増加
- unsafe増加
- platform-specific code増加

となる場合は採用を慎重に判断してください。

性能改善量とmaintenance costを比較してください。


# 29. 正しさを絶対に壊さない

高速化によって、

- precision低下
- rendering quality低下
- data loss
- race condition
- undefined behavior
- security低下
- compatibility低下

を起こさないでください。

近似アルゴリズムを採用する場合は、精度差を測定して報告してください。


# 30. 回帰テストを追加する

最適化したhot pathについて、

```text
この操作では再計算されない
この操作では再allocationされない
この操作では全体rebuildされない
この操作ではnetwork requestされない
```

など、性能上重要な不変条件を可能な限りテストしてください。


# 31. Architectureそのものが原因なら指摘する

局所修正では解決できない場合、

無理にpatchを積み重ねないでください。

例えば、

```text
Immediate mode → Retained mode

Full rebuild → Incremental update

JSON IPC → binary/delta IPC

CPU raster → retained GPU resources

polling → event driven

global state → localized state
```

など、構造変更が必要なら明確に報告してください。


# 32. 最適化の終了条件

「まだ高速化できる」という理由だけで無限に変更しないでください。

以下を満たしたら一度終了してください。

- target latency達成
- p95/p99が許容範囲
- idle負荷が十分低い
- memoryが許容範囲
- 大規模データで実用性能
- 明確なhotspotが残っていない
- 次の最適化の費用対効果が低い


# 実行手順

必ず以下の順番で進めてください。

```text
1. Architecture理解
        ↓
2. Baseline benchmark
        ↓
3. Profiling
        ↓
4. Bottleneck特定
        ↓
5. 原因仮説
        ↓
6. 最小限の修正
        ↓
7. Benchmark
        ↓
8. Regression確認
        ↓
9. 効果判定
        ↓
10. 次のbottleneckへ
```

一度に複数の大規模最適化を行わないでください。

原因と効果の対応関係が分からなくなるためです。

# 最重要ルール

最適化とは、

**「コードを速くすること」ではなく「コンピュータに不要な仕事をさせないこと」**

を第一に考えてください。

特に、

```text
不要な再計算
不要な再描画
不要なallocation
不要なcopy
不要なserialization
不要なIPC
不要なGPU upload
不要なthread
