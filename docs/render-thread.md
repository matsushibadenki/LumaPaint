# macOS描画スレッド設計

## 現状と目的

`canvas_macos.rs`はメインスレッドの`CANVAS`に`NSView`と`Renderer`を保持する。`redraw()`は同じスレッドで`text_editor::render()`からGPU描画を実行する。React側は描画IPCを直列化しているが、SVGのラスタ化、テクスチャ転送、初回GPU構築がAppKitの入力処理を待たせる。

最初の目標は、重いCPU描画準備を入力処理から分離し、古いプレビューを描かずに最新状態へ追いつくこと。GPUと`NSView`の所有を別スレッドへ移すのは、macOSでのサーフェス寿命・表示倍率変更・終了処理を検証した後の独立した工程とする。

## 所有権とメッセージ

- AppKitメインスレッドが`NSView`、`NSTextView`、入力、アクティブ文書、Undo/Redoを所有する。ワーカーはこれらの参照や生ポインターを受け取らない。
- CPU準備ワーカーには、確定済みの文書から作った不変の描画入力、文書ID、単調増加する文書revision、プレビュー世代、キャンバス世代を渡す。描画入力はビュー状態を読みに戻らない。ドラッグ中の一時位置はプレビュー世代に含める。
- ワーカーはSVG／文字のラスタ結果と識別子を返す。メインスレッドは文書ID・revision・プレビュー世代・キャンバス世代がすべて現在値に一致する場合だけGPUキャッシュを更新し、画面へ提示する。Undo、タブ切替、閉じる、再表示、リサイズ後の古い結果は破棄する。
- 中間プレビュー要求はキャンバスごとに最新1件にまとめ、ウインドウ間ではFIFOで処理する。確定した編集の順序と文書履歴はメインスレッドで保持し、準備結果の到着順には依存しない。画面更新は1フレームにまとめ、未表示中は新しいGPUフレームを作らない。
- ワーカーの失敗は該当世代にだけ通知する。古い世代の失敗で新しい成功結果を上書きしない。入力と保存は描画失敗から独立させる。

## サーフェスと終了

第1段階では`Renderer`と`wgpu::Surface`は従来どおりメインスレッドに残す。確定文書のSVG／文字レイヤーを単一CPUワーカーで準備し、結果の転送と`present`をメインスレッドで行う。キューは実行中1件・各キャンバスの待機1件までとし、同じキャンバスの待機分だけを最新要求へ置き換える。別ウインドウの要求は上書きせず、キャンバス間ではFIFOで処理する。文書・キャンバス世代が異なる結果は破棄する。インライン編集中とベクタードラッグ中は同期描画を維持する。ワーカーが参照するフォントDBなどの共有資源は不変として扱う。

将来GPUを専用スレッドへ移す場合は、まず`Renderer`とサーフェスがそのスレッドで安全に所有・破棄できることをmacOSで実証する。`NSView`の作成・フレーム変更・取り外しはメインスレッドに残し、サーフェスがそのビューを参照する間はretainを保持する。終了時は新規要求を止め、描画中の作業を終えるか破棄し、サーフェスを先に破棄してからメインスレッドでビューを取り外す。待機中にメインスレッドへ同期呼び出しする循環待ちは禁止する。

## 実装順と完了条件

1. CPU準備とGPU転送の所要時間、最長入力待ち時間、転送バイト数を計測する。現状の描画経路を基準値として保存する。
2. 不変の描画入力と世代付き結果を導入する。まずSVG／文字レイヤーのCPUラスタ化を移し、ブラシ・選択境界・GPU合成は現行経路に残す。
3. タブ切替、連続ドラッグ、インライン文字編集、設定画面による非表示、ウィンドウ破棄で古い結果が表示・保存されないことを検証する。複数ディスプレイ間の倍率変更、スリープ復帰、デバイス喪失はmacOS実機で確認する。
4. 入力待ち時間と転送量を再測定する。GPUスレッド分離は第1段階の結果とサーフェス寿命の実証に基づいて決める。

この設計は保存形式を変更しない。処理グラフとSparse Tileへの移行時も、文書revisionと世代で結果を照合する契約を維持する。

開発時は`LUMAPAINT_RENDER_METRICS=1`を設定して起動すると、確定文書・インライン文字・ベクタードラッグごとのメインスレッド描画時間と、ワーカー待機・CPUラスタ化・GPU転送時間および転送バイト数を標準エラーへ出力する。実機での入力待ち時間の比較はこの計測を有効にして行う。

テキストフレームのSVGプレビュー解像度を下げる効果は、`cargo run -p lumapaint-renderer --example bench_text_resolution --locked --release`で再計測できる。実際の文書モデルが生成する固定高さフレームを使った2026-09-24のmacOS計測では、5行で2048pxが50.5ms・512pxが48.0ms、45行で2048pxが437.1ms・512pxが423.8msだった。画素数を16分の1にしてもCPU処理は約3〜5%しか短縮されず、現状は品質切替を設けない。これはSVGのCPUラスタ化のみの値で、GPU転送・入力待ち時間を含まない。次は文字解析・字形配置の再利用と実機の入力遅延を計測する。

同じ診断例は、同一ベクターレイヤー内の2つのテキストフレームの片方を更新した場合も測る。フレーム単位のCPUキャッシュを使うと、2048px・各20行のケースでレイヤー全面ラスタ化の平均309.5msが165.6msになった（macOS release、3回平均）。キャッシュは内容フィンガープリントと元SVGの一致・寸法で照合し、64MiBのLRUに収める。現在は変更後のレイヤー全体を合成してGPUへ転送するため、この値に転送時間や入力待ち時間は含まれない。
`LUMAPAINT_RENDER_METRICS=1`ではワーカー要求ごとに、フレームの実ラスタ化数とキャッシュ再利用数、保持件数、計上ペイロードbytes、ペイロード予算、要求内の追い出し数も出力する。計上値は画素とソースの合計で、キー・管理構造・作業画像・GPU資源は含まない。

テキストフレームの枠・リサイズハンドルは文字SVGへ含めず、wgpuで最大120頂点のガイドとして描く。選択／解除や表示倍率の変更だけでは文字レイヤーのsourceとキャッシュを無効化しない。インライン編集の終了時は既存の組版計測キャッシュを利用し、確定した文字のGPU画像を準備してからネイティブ文字ビューを外す。編集内容の初回ラスタ化はこの切り替え時には同期処理であり、長文の組版・ラスタ化自体の最適化は継続課題。

ベクタードラッグ終了時はリリース位置を既存のGPUキャッシュで描画してから文書へ確定する。確定SVGをワーカーが準備している間は、その完全なフレームをサーフェスに保持し、変更レイヤーを省いた中間フレームをpresentしない。リサイズ確定時も同様に直前のプレビューを保持する。保持対象は文書ID・revision・canvas tokenで限定し、すべての表示対象SVGのキャッシュが一致した時点で確定画面へ切り替える。

ベクタードラッグでは `unit_reuse`（レイヤー全体の既存テクスチャ移動）、`partial_reuse`（分割テクスチャの移動）、`cache_builds`（分割キャッシュの新規作成）、`full_previews`（全面プレビュー経路）をフレームごとに記録する。`upload_bytes` はそのフレームでGPUへ渡したRGBAピクセルのバイト数で、`cache_setup_ms` と `full_prepare_upload_ms` は各経路のCPU準備と転送要求に要した時間を示す。GPU実行完了までの時間ではない。

CPU側の分割キャッシュ効果は `cargo test -p lumapaint-renderer --locked vector_drag_raster_cost_diagnostic -- --ignored --nocapture` で再計測できる。960×640の重ならない2図形を24位置へ移動する診断ケースでは、全面ラスタ化は約197 ms・生成ピクセル56 MiB、分割キャッシュの初期化は約0.17 ms・4 MiBだった（2026-09-22、開発用debugビルド）。この数値はGPU転送や実際のポインター入力待ち時間を含まない。図形が重なる場合は正しい合成を保つため全面再描画へ戻るので、実機計測ではその経路も別に確認する。

大規模Sceneの変更Journal、空間インデックス、共有ページSnapshot、キャッシュ予算の移行順は[大規模Sceneと描画キャッシュ](large-scene-rendering.md)を参照。現行ワーカーの存在だけで独立描画スレッドや100万オブジェクト対応を実装済みとは扱わない。

## テキストプレビューの再描画改善（2026-09-30）

文字フレームキャッシュは非同期準備ワーカーだけでなく、rendererの同期経路にも接続する。入力中とボックスサイズ変更中のプレビューで、同じレイヤーの未変更文字を再ラスタ化しない。1個だけのテキストボックスもキャッシュ対象とする。混在レイヤーや元ソースが独自オブジェクトの生成結果と一致しない場合は従来の全レイヤー互換経路を維持する。

キャッシュ用画像はusvgの線・効果を含む描画boundsを文書ピクセルへ写し、整数の原点と2pxの余白を持つ小さなSurfaceで生成する。文書内に制限し、元のscaleと画素位置を維持する。その小画像だけを走査して透明余白を除く。以前の「用紙全体を確保・描画・全画素走査してから切り抜く」処理を避ける。レイヤー合成とGPUテクスチャは引き続き文書寸法を使い、これは完全なDirty Tile描画の実装ではない。

同期rendererと非同期ワーカーは別のキャッシュ所有者で、各キャッシュは計上ペイロード64MiB・512エントリー以内。合計のCPU／GPU予算管理は大規模Scene計画の後続課題。

手動の比較試験は以下で再実行できる。2048×2048、8文字ボックス、デバッグビルド、CPUのprepare_layerのみの試験であり、GPU転送・合成・AppKit入力遅延・アプリFPSは含めない。

```sh
cargo test -p lumapaint-renderer text_frame_render_timing --offline -- --ignored --nocapture
```

同じfixtureの一回の比較では初回616.34→252.02ms、再利用1.19→0.82ms、1個の編集23.63→16.93ms。初回にはフォント初期化を含むため、一般的な速度保証には用いない。回帰試験では三言語、回転・拡縮、用紙端、線、クリップ、ぼかし、空フレームの画素一致を検証し、4096×4096の単独文字でキャッシュ用Surfaceが用紙面積の1/64未満となることを確認する。

検証用macOSアプリの2480×3508文書で、英語・日本語・简体中文の入力、文字サイズ・枠幅変更、確定後の描画を確認した。実機FPSの計測結果とは区別する。
