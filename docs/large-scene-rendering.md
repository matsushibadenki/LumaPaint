# 大規模Sceneと描画キャッシュ

## 採用方針と現在地

目標は「100万オブジェクトを毎フレーム描く」ことではなく、100万オブジェクトを保持していても、通常フレームが変更・表示対象だけへアクセスすること。60fpsの16.67ms、120fpsの8.33msは実機で検証する目標であり、現時点の達成値ではない。添付意見の「100万 → 12」などの数値は説明例であり、LumaPaintの計測結果として使わない。

正本は引き続きRustのLP Document Model。Skia・wgpu・SVG／PDF／AI／Native I/Oは正本へ依存し、描画キャッシュやSceneを保存形式の正本にしない。Vector・Raster・将来のAnimationは共通の表示境界へ接続するが、現在別型のv1文書とタイル文書を統合済みと扱わない。

現在の実装には次の基盤がある。

- `PaintCache`とタイル投影がペイントを保持し、変更タイルを転送する。
- `CachedSvg`がレイヤー単位のGPUテクスチャを再利用する。同寸法の変更は変更行を転送する。
- [Done] macOSの編集可能ベクター／文字のオブジェクトキャッシュは、対応する単色パスをSkia Metalからwgpuへ共有テクスチャで渡す。CPU画素読み戻しと再uploadを省略し、移動・パン・ズームでは既存テクスチャを再利用する。非Metal・未対応SVG・共有初期化失敗時は従来経路へ戻す。GPUの計上メモリは引き続き64MiB以内、診断のupload_bytesは実転送のみを数える。
- `FrameRasterCache`が文字フレームの描画結果を実際の画素範囲へ切り詰め、CPUキャッシュの計上ペイロードを64MiB・512エントリー以内に制限する。Undo/Redoでも以前の版を再利用する。
- `svg-raster`・`tile-project`ワーカーが重い処理を行い、待機要求を最新のものへまとめる。文書・表示キーで採用結果を確認する。
- `LUMAPAINT_RENDER_METRICS=1`で描画、待機、ラスタ化、転送量を記録する。文字キャッシュの件数・計上ペイロード・予算・追い出し数も記録する。

現状のSVG描画はレイヤー単位で、レイヤーのソース比較、オブジェクト探索・SVG生成、ペイント履歴の比較などに全走査が残る。変更Journalと個別世代は編集・Undo/Redo・削除・読込に接続済み。選択用BVHと対応する単色ベジェの描画用BVHも実装済み。通常のベクター移動は変形値だけの履歴と局所Journal通知に移行し、LP生成SVGの変形スロットを直接更新する。対応する単色ベジェの描画BVHは移動とUndo/Redoで局所refitする。BVHノードは256要素の共有ページに保持し、複製した旧版と新しい版を独立して参照できる。ただしScene Compilerによる文書全体のimmutable RenderSnapshot公開と変更対象だけの文書更新は未完成。処理グラフは効果・合成の依存DAGであり、空間的なScene Graphの代用ではない。

また現在は編集可能ベクターレイヤーごとに4096オブジェクト、SVGレイヤー16、SVGソース合計6MiB、v1ファイル64MiBという制約がある。上限を先に外して100万対応と称さない。Sceneと保存・読込・履歴・選択・メモリの検証後に、新しい文書容量契約として拡張する。

## 依存とデータの流れ

### GPU描画の段階的な拡張

- [Done] Zero-copy GPUの第一段階：macOSのオブジェクトキャッシュ。wgpuの実Metal Deviceからテクスチャを確保し、Skiaは同じDeviceで描画する。透明領域を含め初期化し、Skiaとwgpuが同じ実Metal queueを使用することで提出順序を維持する。保存・CPU差分比較・外部SVG互換・workspace画像のRGBA経路は維持する。共有経路ではCPUの完了待ちを行わない。Deviceとqueueの組でコンテキストを分け、複数ウインドウ間で誤ったqueueを使わない。
- [Next] 変更Journalとgeometry／style／transform世代、BVHによる可視範囲検索を追加し、変更対象だけSceneを更新する。次いでVector／Group／Effectの局所タイルキャッシュ、互換SVGの共有GPU出力と非同期queue同期へ拡張する。
- [Later] GPU resident vector scene：Geometry／Style／Transform／BoundsをGPUへ保持し、表示用precisionとzoom bucketを管理する。Documentの精度や保存データは変えない。
- [Later] GPU-driven renderer：GPU可視判定とindirect drawingを段階導入する。GPU-native Bézier／analytic AAは複雑なfill・stroke・互換性を検証してから追加し、Skia／resvgを併用する。RGBA16F・linear-light合成とICC変換は別の品質検証工程で扱う。

```text
LP Document ─────────────────────────→ 独立I/O
    │ 編集トランザクション / Undo / Redo
    ▼
Change Journal（変更ID・種類・世代）
    ▼
Scene Compiler（Rustワーカー）
    ├─ Geometry / Styleの参照と世代
    ├─ 階層・空間インデックス・描画順
    └─ 効果・クリップ・合成への無効化伝播
    ▼
Immutable RenderSnapshot（共有ページ）
    ▼
Viewport Query → Render List → Vector / Raster描画
    ▼
Tile / Group / Effect Cache → wgpu Compositor → 画面
```

coreはLP固有の編集結果・変更IDを提供し、rendererは派生SceneとGPU資源を所有する。SkiaのPathやSurface、フォント・SVG解析ツリーはrenderer／アダプター内部に保持する。各Tauriウインドウは表示条件とSceneへの参照だけを持ち、Documentの正本を所有しない。大容量画素・geometry・snapshotはRust内に置き、WebViewへは設定・操作・診断値だけ渡す。

## 1. 全走査を変更Journalへ置き換える

最初に計測と世代管理を整える。各オブジェクトの安定IDにgeometry・transform・style・effect・childrenの世代を持たせる。選択ハイライト、ビュー変更、文書内容変更を区別する。移動だけならgeometryとstyleを再生成しない。不透明度だけで再利用できる単独グループは合成状態だけ更新する。

編集・Undo・Redo・削除・読込・文書切替を同じ変更通知契約へ接続する。トランザクションの成功時だけJournalへ追加し、失敗時は状態とJournalの双方を変更しない。Journalを購読する描画・サムネイル等には消費位置を持たせ、通知欠落や世代の不連続時だけ全再構築する。

変更件数はその編集に比例させる。ただしグループ変更や共有スタイル変更が多数の子へ影響する場合は、その実際の依存範囲を処理する。毎フレームの全SVG文字列比較・全履歴比較を世代キーへ置き換え、SVG文字列の再生成はI/Oや互換描画が必要なタイミングへ限定する。

## 共有ページと可視判定の実装状況

- [Done] coreの`scene::pages::Pages`は256要素の葉と32分岐・4階層の共有radix treeを使用する。複製はrootのArc共有、変更は経路と対象ページのみのcopy-on-write。選択BVHのノード格納へ接続し、葉の参照表とunknown一覧も旧版と共有する。
- [Done] 100万要素の単体テストで旧版の値を維持し、1要素変更の要素clone数が256であることを確認。10万葉のBVHでは旧版を保持したrefitと新旧それぞれの検索結果を検証する。これはデータ構造の検証であり、アプリの100万オブジェクト対応やfps測定ではない。
- [Done] 対応する単色ベジェのGPU描画はBVHで画面内の候補を抽出し、その描画順でgeometry更新・indirect drawを行う。2画面ピクセルの余裕と、移動中の選択オブジェクトを含める。変更のないuniformとindirect bufferの再転送も省く。
- [Done] 通常移動とUndo/Redoは変形値と旧新描画範囲だけを履歴／Journalに保持。選択用ID索引を再利用し、単色ベジェ描画BVHは変更葉と祖先だけrefitする。静止時の全ID収集と作品バッファの転送を省く。構造変更・Journal欠落・別文書・別forkは全構築へ戻す。
- [Next] 互換SVGソースはまだStringで保持する。通常移動は固定長スロットと位置索引で全シリアライズ・ウォーム時の検索・後続バイトの再配置を省く。認証済み保持画像キャッシュもJournalから変形差分を受け取る。未対応の互換キャッシュ生成にはレイヤーサイズに比例する処理が残る。遅延SVG生成と共有Scene、一般編集の差分履歴、未対応描画のSnapshot公開を続ける。

## 2. 空間インデックスとコンパクトなScene

Sceneは連続メモリの固定サイズページに分ける。RenderNodeは数値ID、world bounds、transform、描画順、geometry/style参照、clip/effect/合成スコープ参照などを持ち、文字列・パス本体・画素を複製しない。削除後に同じ番号を使う場合はgenerationも照合する。

初期候補はオブジェクトのAABBを葉にしたBVH。ビューと交差する枝だけ辿り、ヒットテストでも同じ候補を使う。変更葉と祖先のrefitを基本とし、偏りが大きくなった部分木の再構築はワーカーへ回す。大量追加・初回読込は全構築を許容し、通常の1個移動で全構築しない。可視候補は最終的に安定した描画順へ並べる。BVHの列挙順で合成しない。

インデックスには中心線のboundsではなく、線幅・矢印・フィルター等を含む描画boundsを入れる。選択許容距離は画面座標から文書座標へ換算する。グループ単位でも早期棄却し、非表示、クリップ、グループ不透明度の意味を維持する。ズームアウトで全件が候補になる場合は、空間インデックスだけでは高速化できない。

## 3. Dirty範囲と正しい部分再合成

移動・削除の基礎範囲は変更前後の描画boundsの和集合。境界を跨ぐ移動では旧領域も必ず無効化する。アンチエイリアスとフィルターの周辺入力を加え、クリップ・マスク・効果・合成DAGを通して影響先へ伝播する。影響範囲を宣言できない処理は、対応スコープ全体を無効化する。

Dirtyタイルを再描画するときは、そのタイルに寄与する背面から前面までの要素を元の順序で再合成する。「変更した円だけを既存画像へ描き足す」では、移動前の円や半透明の重なりを正しく消せない。未変更要素はgeometryやgroup textureを再利用できるが、必要な合成まで省略できるわけではない。

ぼかしのタイルはhalo付きで作り、出力の中央領域だけ採用する。孤立グループ不透明度、ブレンド、クリップ、効果があるスコープは独立合成単位とする。レイヤー順・親子構造・共有スタイルの変更も依存する範囲へ伝播する。保存パス・選択枠など編集オーバーレイは作品Sceneと別に合成する。

## 4. 複数キャッシュを予算内で使う

Geometry、Style、Render List、Group Raster、Vector Tile、Effect、Mipのキャッシュを別の寿命とキーで管理する。キーには文書ID、対象IDと世代、色条件、画素形式、表示解像度・zoom bucket、clip/effect入力世代を含める。単なるDocument全体のrevisionで全キャッシュを失効させない。

Raster／Effectの予算はCPUとGPUで別々に持ち、全ウインドウ・文書の合計も制限する。2GB固定を前提とせず、まず保守的な設定予算で実機計測する。LRUを初期方針とし、可視性・再生成コスト・再利用実績による優先度は後から追加する。巨大で単発の結果はキャッシュせず、タイル化か互換経路を選ぶ。

追い出しは画面の作品を変えず、次回のcache missを発生させるだけにする。処理中・描画中の資源は完了まで保持するが、その分もメモリ診断へ別計上する。現在の文字キャッシュの64MiBは画素とソースの計上値であり、HashMap・キー・Arc・作業画像・GPU資源を含むプロセス全体の上限ではない。

## 5. LODと公開Snapshot

最初は正確なgeometryとキャッシュ画像の切替を実装し、geometry簡略化は後続にする。縮小時にオブジェクトを個別に捨てると、細線や密集した半透明要素の外観を変えるため、グループ／タイルの合成済みMipを優先する。screen-space errorは輪郭だけでなく線・文字・効果・合成後の画像で評価する。編集・書出しは正確なモデルを使い、表示LODを保存・I/Oへ流さない。

Scene Compilerの可変状態と公開Snapshotを分ける。変更ページとインデックスの変更経路だけをcopy-on-writeで更新し、未変更geometry・style・ページをArcで共有する。100万件のDocument cloneやVec cloneをフレームごとに行わない。完成した整合性のあるSnapshotだけ短い公開処理で交換し、レンダラーはフレーム中、同じ版を参照する。

ワーカー結果には文書ID・内容世代・表示条件を持たせる。古い文書や不要になったzoom bucketの結果を採用しない。待機ジョブは最新要求へまとめ、生成中も表示を停止しない。ただし古いSnapshotの再表示と最新内容の完成を区別し、遅延やキャンセルを計測する。表示スレッド移行はnative viewとwgpu surfaceの寿命を検証して段階的に行い、UIイベント処理と大きなDocument lockを分離する。

Animationは現在時刻で値が変わったノードだけをJournal相当の入力として渡す。静止Vector・Rasterを毎時刻再構築しない。カメラ／全体効果が変わる場合は実際に必要な可視・合成範囲を更新する。

## 実装順と合格条件

| 段階 | 優先内容 | 完了の証拠 |
| --- | --- | --- |
| 1 | 計測拡張、変更Journal、個別世代キー | 静止時の不要な準備・転送がゼロ。1個移動で全SVG生成・全件比較が発生しない |
| 2 | オブジェクト／グループbounds、BVH、選択への接続 | 境界外・矢印・効果を落とさず、線形探索と結果が一致。検査ノード数も記録 |
| 3 | 共有ページScene、immutable Snapshot | 1個編集のコピー量が総件数に比例しない。旧Snapshotが安全に描画でき、削除・Undo・文書切替で古い結果を採用しない |
| 4 | Vector Tile／Group／Effect部分再合成、共通予算 | フル再描画との画素差、ぼかし継ぎ目、半透明・順序・クリップを検証。予算超過時の追い出しと復元が正しい |
| 5 | 表示LOD、Mip、描画スレッドの分離 | zoom切替・cold cache・低メモリでも作品を欠落させない。入力遅延とGPU時間を実機で確認 |
| 6 | 新容量契約と10万／100万規模の読込・保存・編集 | 全経路のメモリ・時間・復旧・Undoを検証後に容量上限を拡張 |

各段階を完結してから次へ進む。Sceneの追加だけで既存のレイヤー互換描画を撤去せず、同じfixtureで描画・選択・Undoの一致を確認して切り替える。

## 性能試験の契約

10万／100万件は、新容量モデルのfixtureで測る。初期段階は現行上限内とScene単体の合成fixtureを区別する。単体インデックス試験をアプリのFPSとして報告しない。

疎な配置、一画面に密集する配置、深いグループ、半透明、文字、太い線・矢印、クリップ、ぼかし、大きな画像を含める。静止、1個移動、100個編集、パン、連続ズーム、全景表示、Undo/Redo、文書切替、cold/warm cache、予算超過を測る。入力件数だけでなく、画面内件数・実際の更新件数・合成draw数・キャッシュ使用量を併記する。

記録項目はCPU各段階とGPU時間のp50／p95／p99、入力から表示までの遅延、frame deadline超過、走査／refit数、再生成geometry数、dirtyタイル数、hit/miss/eviction、CPU／GPU保持・作業メモリ、転送bytes、古い結果の破棄数。測定機種、GPU、解像度、refresh rate、ビルド種別、thermal状態、fixtureも残す。

60／120fpsはwarm cacheの通常操作から段階的に評価し、ロード時間やcold cacheの再構築は別に報告する。密集した全景、巨大効果、キャッシュ不足で目標を下回る場合は、その条件を明示する。現段階で全条件の60／120fpsは保証しない。

## 通常移動の差分トランザクションと計測（2026-10-05）

`Document::translation_metrics()`は最後に成功した移動／差分Undo／Redoの経過時間、Journal時間、変更数、ID索引の全走査数、変形履歴の保持バイト数、全レイヤー履歴数、SVG全生成数、変形スロット更新バイト数、ソース検索バイト数、ソースの推定再配置バイト数を返す。履歴バイトはtransform/boundsエントリーのみで、選択ID、Vec容量、allocator、検証作業領域、プロセス全体のメモリは含まない。推定再配置はStringの桁数変更と容量拡張の上限計上で、実測メモリ帯域ではない。

LP生成ソースでは1個移動時の全SVG生成と全レイヤー履歴複製をゼロにする。旧形式や別の構造を持つ読み込みSVGは読み込み時に正規ソースとの一致を検証し、移動時は正規化＋全状態履歴へ戻す。保存パス編集も第二の正本への同期を必要とするため全状態履歴を維持する。これらのフォールバックを差分経路の達成件数には含めない。読み込み時、構造変更時、初回ID索引構築時の全走査は許容する。

`LUMAPAINT_RENDER_METRICS=1`の`lumapaint-native-preparation`には全ID走査、SVG生成、BVH構築/refit、geometry生成とGPUバッファへの初期化・更新量を出す。これは単色ベジェの準備経路の診断であり、全レンダラーのGPU時間、画像転送、入力遅延、VRAM計測を置き換えない。

```sh
cargo run --release -p lumapaint-core --example bench_translation -- --seconds 60 --runs 5
```

このベンチマークは1,000／4,096個の矩形を保持し、20回のウォームアップ後、移動・Undo・Redoのp50／p95／p99、8.33／16.67ms超過率をCSVへ出す。保存／再読込のRustコア状態も10回測る。既定は0.25秒×1回の実行確認用。画面・WebView・GPU・文字・クリップを含む現行アプリの測定、Scene単体の10万／100万ケース、大容量対応後のアプリ全経路の測定は別工程として残る。短時間のコア測定から60／120fps達成を判定しない。

次の実装順は、SVG遅延生成を含む差分編集の完成、グループ・効果を含む局所タイル更新、キャッシュ総予算と縮小画像、GPU描画対象の拡張、大容量保存・復旧とする。アプリ比較は同一機種・解像度・Release条件でウォームアップ後60秒×5回を記録し、全景表示・強い重なり・初回表示・保存中の操作性を独立して評価する。Adobeとの画質比較はフォント・ICC・解像度を揃え、輪郭・文字・透明度・合成順・色を個別に確認する。

短時間測定と前段階の結果は[通常移動の差分処理・測定結果](translation-benchmark-2026-10-05.md)に記録。対応するウォーム移動のソース更新量は一定になったが、アプリ全経路のコピー量・フレーム時間は未検証。

## 固定長スロットと保持画像の差分確定

[Done] 平行移動のe/fを18文字・小数部9桁の科学表記にして、有限f32の往復を保つ。標準SVGとして有効な空白を使い、従来ソースより可視オブジェクト当たり概ね34バイト増える。初回はソースから位置索引を作り、構造編集・全状態復元・文書複製時に捨てる。通常移動は同じ長さの範囲だけ更新し、末尾のオブジェクトでもソース全体を検索しない。旧非正規ソースの正規化は従来の容量検証と全状態履歴を使う。
