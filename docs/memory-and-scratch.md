# Memory and scratch disks

Preferences → Performance shows physical RAM, process resident memory when the OS supports it, estimated resident managed history and temporary scratch bytes. RAM allocation is editable as a percentage or MiB, defaults to 70%, and accepts 10–90%. History states default to 50 and accept 1–1,000. Preferences → Scratch Disks enables locations and orders their priority. Settings and errors are available in English, Japanese and Simplified Chinese.

The Photoshop reference is Adobe's [Performance preferences](https://helpx.adobe.com/uk/photoshop/using/performance-preferences.html). LumaPaint's allocation is a **soft policy for managed undo history and text raster caches**, not a process-wide memory ceiling. Current artwork, document/page snapshots outside the managed history, GPU resources, WebView memory and transient buffers are outside that budget. One quarter of the chosen allocation is divided among authoritative open documents; cache allocations also retain their existing upper bound. Two recent entries on each history stack remain in RAM for interactive Undo/Redo. History estimates are approximate, including shared data conservatively.

The Rust core owns undo entries and receives a storage adapter; the Tauri host owns filesystem access. Cold vector-state and tiled raster history is serialized to private per-session temporary files when the budget is exceeded. Undo/Redo reads those files and checks length and checksum before changing the model. A failed write leaves the original entry in RAM; a failed read leaves history and artwork unchanged. Saved projects do not contain scratch paths. Shared editor windows do not duplicate the document budget. Lowering the history count removes oldest available states without deleting current artwork.

The first enabled writable disk with at least 1 GiB plus the incoming payload free is used; failures fall through to later enabled disks. The startup volume uses the application cache directory, while custom locations use a `.lumapaint-scratch` directory. Applying settings checks write access and free space and atomically saves `performance.json` in the application config directory. Existing files remain readable on their original location after priority changes. Files are removed when their final history reference is released; the application's own session directories are removed on normal shutdown.

Scratch storage is temporary and does not replace project saving or recovery. Live artwork tiles and page-book snapshots are not paged. Serialization and history transfers currently run with native edit commits and can introduce latency under heavy memory pressure. Automatic cleanup after crashes, background paging and a broader tile/GPU memory governor remain future work. Disk availability is checked at each write; unplugging a disk holding history produces an error until that disk becomes available again.

Validation covers real filesystem paging, exact vector/raster Undo/Redo, failed writes without data loss, history-count limits, disk fallback, corruption detection, reference lifetime cleanup, native RAM/free-space reporting on macOS, and 54 settings interactions across all three languages at 640px and 1200px widths. Windows/Linux OS queries and device-level full-disk/unplug/crash scenarios require platform validation.
