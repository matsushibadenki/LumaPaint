# 画像レイヤー移動のGPU保持（2026-11-04）

指定された `illust.png`（1672×941、SHA-256 `f768ef967b2ecf704f8bfebb3d8d683079690686cfcb64306e57757e2d71054b`）をmacOS Tauriで開いて検証した。画像自体はリポジトリへ追加していない。

## 変更

従来はドラッグのたびに描画用Documentを複製し、画像を埋め込んだSVGの移動版を生成して再描画していた。確定直後にもキャンバス外表示用の画像を再生成し、今回の実機では数百msを要した。

通常の画像レイヤー移動は、RustのRendererが保持するGPU画像を同じレイヤー順で描画し、移動量のみGPUへ渡す。キャンバス内に収まる画像は表示済みテクスチャの所有権を移し、初回の画素転送も省略する。元のSVGキャッシュから取り出すため、非同期ワーカーによる上書きで移動画像が二重にずれることを防ぐ。キャンバス外に元画像がある場合は全内容の局所テクスチャを用意する。画面倍率とバックングスケールに応じた密度を使い、HiDPI・高倍率で1倍画像を引き伸ばすだけにはしない。

確定時は文書ID相当のjournal identity・編集前revisionを照合し、同じ移動の確定だけをGPU矩形更新で引き継ぐ。他の編集・文書切替・Undo／Redo・不透明度変更はsource identityなどで無効化する。画像の境界情報も再利用する。通常のオブジェクト画像キャッシュと合計64MiBの保持枠を共有する（他のSVG・workspaceキャッシュ、ドライバーの実割当、一時準備領域は別）。データと履歴はRustが所有し、WebViewへ画素を転送しない。

マスク・レイヤー効果・文書クリッピング・アウトライン・チャンネル表示・Optionによる複製・予算を超える画像は既存の合成経路を使う。複製時の半透明合成とグループ不透明度を変えないため、複製には今回の高速経路を適用しない。

画像移動のRust実装があるのにフロントエンドが選択ツールを無効にしていた判定も修正。通常選択とダイレクト選択を画像レイヤーでも使用でき、V／Aも共通判定を使う。非表示・ロック・マスク編集先等の制限と英語・日本語・简体中文の既存理由表示は維持する。

## 実測

Apple M4 / Metal、Tauri debug（core/rendererは既存設定のopt-level=2）、800×554物理ピクセル、backing scale=1、表示44.98%。同じ画像を80×50画面ポイント往復移動。各列4操作の中央値。

| ホスト処理 | 従来経路 | 改善後の再利用時 |
|---|---:|---:|
| 押下処理 | 386.67 ms | 6.57 ms |
| 移動確定処理 | 519.26 ms | 60.70 ms |
| 確定時のキャンバス再描画 | 393.49 ms | 2.14 ms |

改善後の最初の押下は252.02msで、上表の再利用時とは分離した。初回の境界解析等が残っている。確定後のSVG生成・履歴・UI通知等も残る。画像のGPUアップロードは初回の表示テクスチャ移管と通常倍率での再利用中は0 bytes。200%では必要な密度の画像を一度準備し、以後は再利用する。

比較前は初期検証ビルドに `LUMAPAINT_PIXEL_DRAG_BASELINE=1` と `LUMAPAINT_RENDER_METRICS=1` を指定して従来経路を使用。比較後は境界・確定の再利用を追加した検証ビルドでbaseline指定を外した。両方とも同じdev最適化設定。バックグラウンド負荷は隔離しておらず、少数の操作試料である。ツールが送る短いドラッグはイベントが合流するため、連続ドラッグのFPSや物理ディスプレイ遅延、厳密なp95/p99を示す値ではない。
